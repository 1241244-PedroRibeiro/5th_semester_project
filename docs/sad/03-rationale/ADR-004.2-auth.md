# ADR 004.2: Revocable JWT Authentication Sessions

- **Status:** Accepted
- **Date:** 2026-11-04
- **Decision Makers:** LaPrizza Development Team
- **Relationship:** Partially supersedes [ADR-004](ADR-004-auth.md) for session verification and logout. The original record remains unchanged as architectural history.

## Context

ADR-004 selected JWT authentication with Argon2id password hashing and explicit bearer-header transport. It accepted self-contained JWT verification and delayed invalidation until token expiration to avoid server-side session state.

The logout requirement now states that an ended session must not be reused for protected operations. Testing demonstrated that a copied bearer token could still change application data after the browser logged out. Deleting a token from browser storage does not invalidate the credential on the API. Checking its signature and expiration alone cannot enforce immediate logout.

The application already uses NestJS, PostgreSQL, and TypeORM. The change should reuse that infrastructure, preserve independently issued logins, and keep session rules separate from credential transport so a future HttpOnly-cookie migration can reuse them.

## Decision

Adopt **PostgreSQL-backed, revocable authentication sessions linked to bearer JWTs**, while retaining Argon2id password hashing, role-based authorization, and the existing 15-minute JWT lifetime.

1. **Session creation and issuance:** Successful login and registration create an unpredictable UUID v4 session ID. The JWT contains `sid`, `sub` (username), `email`, `roles`, `status`, `iat`, and `exp`. Persist the session before returning the token, with the same expiration as the JWT. No raw JWT is stored in PostgreSQL.
2. **Session persistence:** Store `id`, `username`, `expires_at`, and nullable `revoked_at` in `auth_sessions`. The username references `users(username)` with cascading deletion. TypeORM migration `AuthSessions1793836800000` and SQL script `015_create_auth_sessions_table.sql` create the same table and expiration index. Either creation path can run first without deleting session records.
3. **Protected request verification:** Validate the HS256 signature and expiration, require a valid `sid`, and load its session. The session must belong to `sub`, remain unrevoked, and be unexpired. The global `AuthGuard` also reloads current account roles and status before authorization. The additional `JwtAuthGuard` uses the same session rules through `JwtTokenService`. Session lookup failures prevent protected execution and propagate as server errors.
4. **Server-side logout:** `POST /auth/logout` authenticates the current credential, revokes only its session, and returns `204` after persistence succeeds. Independently issued sessions remain active. Missing, invalid, expired, unknown, legacy sessionless, or already revoked credentials return `401`. Logout requires no particular role or active-account status.
5. **Frontend confirmation and failure handling:** Angular waits for server confirmation before clearing local credentials and redirecting. A `401` means the credential is already unusable and can be cleared. Network errors and server failures retain local state, display an error, and allow retry. Local cleanup after authentication failure does not send another logout request.
6. **Credential transport:** Retain `Authorization: Bearer <token>` and the existing `forno-session` browser storage behavior. No cookie transport or refresh tokens are introduced. A future HttpOnly-cookie migration must preserve session creation, lookup, and revocation, while adding cookie issuance/deletion and CSRF protection.

### Domain encapsulation

`domain/user/AuthSession` represents one login session independently of JWTs, cookies, NestJS, and TypeORM. It owns session-ID validation, ownership and expiration checks (`isActiveFor`/`isActive`), and irreversible, idempotent revocation (`revoke`). It uses the existing `Username` and immutable `Timestamp` value objects. Reconstitution preserves expired/revoked state, and callers cannot change session timestamps through getters.

`IAuthSessionRepository` creates, loads, and saves domain sessions. `AuthSessionMap` translates between the domain object and `AuthSessionEntity`. Guards ask the domain object whether it is active for the credential's subject. `AuthService.logout` loads the domain object, revokes it, and saves it. Persistence conditionally updates only revocation state, preserving the first recorded revocation so an older copy cannot reactivate the session.

## Considered Alternatives

### 1. Keep self-contained JWT verification until expiration

- **Description:** Clear browser storage at logout and let issued JWTs expire naturally, optionally shortening their lifetime.
- **Advantages:** No session table or database lookup on protected requests.
- **Disadvantages:** Copied credentials remain usable after logout, so this does not satisfy the requirement.

### 2. Maintain a JWT revocation denylist

- **Description:** Record revoked token identifiers and check them on every protected request until expiration.
- **Advantages:** Supports immediate token revocation while retaining JWT transport.
- **Disadvantages:** Still requires shared server-side state. Explicit per-login session records provide a direct representation of ownership, expiration, and revocation for the selected domain model.

### 3. Move the JWT to an HttpOnly cookie without server revocation

- **Description:** Change browser credential storage and delete the cookie at logout.
- **Advantages:** Reduces direct access to the credential from browser JavaScript.
- **Disadvantages:** Deleting a cookie does not invalidate a copied JWT. Cookie transport also requires coordinated browser and CSRF changes, which are outside this implementation.

### 4. Introduce Redis-backed opaque sessions

- **Description:** Replace JWTs with opaque session credentials backed by a shared Redis service.
- **Advantages:** Supports centralized session invalidation.
- **Disadvantages:** Introduces another infrastructure dependency and changes the credential contract. Existing PostgreSQL persistence can satisfy the current requirement without adding a service.

## Consequences

### Positive

- **Immediate session revocation:** Protected requests sent after logout completes reject the ended session, including copied credentials.
- **Independent logins:** Ending one session does not end separately issued sessions for the same account.
- **Shared enforcement:** All API instances consult the same PostgreSQL state; no sticky sessions or process-local revocation cache are required.
- **Encapsulated rules:** Session lifecycle rules live in the domain and can be retained when credential transport changes.

### Negative / Trade-offs

- **Database dependency:** Every protected request needs a session lookup. This replaces ADR-004's self-contained-verification trade-off; a database outage prevents protected operations.
- **Deployment compatibility:** Apply the session migration before starting the updated API. Previously issued tokens without `sid` require a new login. Legacy baseline adoption records only the historical initial migration; forward migrations must run normally afterward.
- **Record maintenance:** Expired rows may be deleted using `expires_at <= NOW()`. No cleanup scheduler is introduced. Deleting a session record keeps its credential unusable.
- **In-flight operations:** Requests authenticated before revocation may finish. Logout does not undo completed work.

## Verification

Domain tests cover ownership, the exact expiration boundary, irreversible/idempotent revocation, reconstitution, and protection of timestamps from external mutation. Jest/Supertest tests replay reads and writes after logout, assert unchanged data, and verify independent logins and rejection of legacy, unknown, mismatched, and expired sessions. PostgreSQL tests verify mapping, persisted revocation, stale-save protection, cascading deletion, schema alignment, and both creation paths. Playwright tests cover logout confirmation, failure/retry, already rejected credentials, and staff logout.
