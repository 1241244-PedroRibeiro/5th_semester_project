
# ADR 016: Kitchen Configuration UUID Identity

- **Status:** Accepted
- **Date:** 2026-11-11
- **Decision Makers:** LaPrizza Development Team
- **Supersedes:** ADR-011 (Business Identifier decision only)

## Context

WEB06 requires each kitchen configuration to have a
unique identifier, a descriptive name, JSON content,
and an active or inactive status.

The previous ADR-011 identified each KitchenConfiguration
using its name as the primary key.

This coupled the technical identity of a configuration
to its descriptive business name.

As a consequence, renaming a configuration required
changing its identity and all references based on that
name.

This also limited the integration flexibility of WEB06
with VIS01.

## Decision

KitchenConfiguration will use a generated UUID as its
technical primary identifier.

The database structure will contain:

- id: UUID primary key, generated by PostgreSQL.
- name: VARCHAR(100), unique and editable.
- json_content: JSONB containing the kitchen layout.
- is_active: BOOLEAN indicating the active configuration.
- created_at: TIMESTAMPTZ.
- updated_at: TIMESTAMPTZ.

The name remains unique to avoid duplicate configuration
names in the Manager interface.

The UUID is immutable and is used by REST operations
that identify a specific configuration.

## Active Configuration Invariant

The existing partial unique index is preserved:

CREATE UNIQUE INDEX uq_active_kitchen_configuration
ON kitchen_configurations (is_active)
WHERE is_active = TRUE;

Activation remains transactional.

A configuration must pass JSON and asset validation
before it can become active.

## API Consequences

The following endpoints use the UUID:

- GET /api/kitchen-configurations/:id
- PUT /api/kitchen-configurations/:id
- DELETE /api/kitchen-configurations/:id
- POST /api/kitchen-configurations/:id/activate

The active configuration endpoint remains:

GET /api/kitchen-configurations/active

All configuration responses include both id and name.

## Consequences

### Positive

- Configuration identity is independent of its name.
- Names can be changed without changing the UUID.
- VIS01 can retain a stable configuration reference.
- API operations use immutable identifiers.
- The database preserves name uniqueness.

### Trade-offs

- Existing API consumers must migrate from name-based
  identifiers to UUID-based identifiers.
- Existing database records require a migration.
- Frontend, backend and API documentation must be updated.
