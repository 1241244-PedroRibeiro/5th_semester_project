## 3. Content Creation

### 3.1. Backend Development and Refactoring

I used AI assistance to support implementation and troubleshooting around registration, login, authorization, user information and dietary restrictions. Related work included profile contact details and pizza component-type functionality.

I also used assistance when analysing the effects of changes to domain identities and persistence. These changes required consistency across entities, DTOs, controllers, services, repository interfaces, database mappings and tests. AI helped inspect dependencies and suggest adaptations; a proposed change still needed to respect the project's architecture and business rules.

### 3.2. Test Preparation and Maintenance

AI supported the preparation and review of automated tests, particularly Bruno requests and assertions associated with BCK01, BCK02 and BCK07. Relevant concerns included authentication tokens, setup data, request ordering, validation errors, permissions and pagination.

This assistance helped investigate whether a failure came from application behaviour, an outdated assertion or a missing setup dependency. Expected outcomes needed to follow the requirements rather than simply reproduce whatever response the application returned.

### 3.3. Documentation and Diagrams

I used AI to help organise technical explanations and review documentation against the implementation, including material related to BCK01, BCK02 and BCK07.

A concrete example was the revision of the use-case diagram. I requested an updated view of developed functionality and explicitly explained that an endpoint for recording a phone number or address should not automatically become a separate use case. Those operations belong to a broader user goal, such as completing and maintaining a profile. I also requested a separate version for review before replacement of the original.

AI assisted in preparing this report and the earlier summaries of my AI usage.

## 4. Content Review

I used AI as an additional reviewer to compare requirements, documentation and source code. The review focused on whether routes were actually exposed, whether permissions matched the intended actors, and whether services and persistence supported the documented behaviour.

For the use-case diagram, checking only the API specification would have produced an inaccurate description of developed functionality. The review identified differences between documented routes and mounted controllers, as well as ordering and kitchen functionality that existed only partially in the domain code. This distinction helped separate implemented user goals from planned capabilities.

Review also covered consistency after backend changes, including identifiers, request and response fields, error handling and test dependencies.

## 5. How I Challenged AI Outputs

I challenged AI output by refining the instructions and requiring evidence from the project. Concrete examples include:

1. **Correcting the level of abstraction.** I required the diagram to describe user goals rather than create one use case for every endpoint or profile field.
2. **Requiring multiple sources.** I explicitly asked for both API documentation and code to be considered, because documentation alone could describe outdated or unimplemented behaviour.
3. **Keeping changes reviewable.** I requested a new diagram file so the proposed result could be compared with the original before replacement.
4. **Questioning personal attribution.** After receiving a project-level AI summary, I requested a first-person account of my own usage. This distinction matters because team activity does not establish individual use of a tool.
5. **Checking technical proposals.** Suggested implementation and test changes needed to be assessed against acceptance criteria, authorization rules, domain constraints and the actual project structure. A plausible explanation or a passing assertion alone would not establish correctness.

Compilation, relevant tests and inspection of actual responses are appropriate checks for code changes. Documentation changes require a different check: whether their claims match the implementation. For example, structural checks on a Mermaid file do not establish that its rendering has been visually verified.

## 6. Benefits, Limitations and Responsibility

AI helped organise work, inspect related files, draft documentation and explore possible causes of failures. Its usefulness depended on the context supplied and on how critically I evaluated the result.

The available records do not provide a complete prompt history, a reliable percentage of AI-generated code or a measured estimate of time saved. My development-process report records contributions, but Git authorship alone does not prove which individual changes were AI-assisted. Likewise, this report does not claim that every generated suggestion was accepted or that every workflow passed a fresh test run.

I remain responsible for understanding the submitted work, explaining technical decisions and checking that accepted changes satisfy the requirements. AI assistance was part of the development process, and its outputs required assessment rather than automatic acceptance.
