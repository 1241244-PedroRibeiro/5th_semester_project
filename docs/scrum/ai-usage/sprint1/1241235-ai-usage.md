# Report on AI Usage, Validation, and Human Oversight in the LaPrizza Engineering Process (Sprint 1)

**Project:** LaPrizza Back-End Application  
**Contributor:** 1241235  
**Focus:** API testing, Bruno test maintenance, troubleshooting, and validation around BCK10 and BCK11

---

## 1. Purpose and Working Principles

Artificial Intelligence (AI) was used as a development aid during work on the LaPrizza back-end, not as a replacement for engineering judgement. Its role was to help interpret errors, structure test scenarios, review consistency between API behaviour and test expectations, and make debugging more systematic.

AI-generated suggestions were treated as hypotheses. Changes still needed to be checked against the repository, the API contract, the database state, and the output of actual test runs. A suggestion was not considered correct merely because it looked plausible.

## 2. Where AI Assistance Was Useful

### 2.1. Bruno API Test Analysis and Maintenance

**Area:** `backend/tests/bruno/LaPrizza/`

AI assistance was used to reason about Bruno collection structure, request setup, test assertions, and issues that can arise when tests are executed in a different order or on a different developer's machine. This was particularly relevant to the BCK10 predefined-pizza tests and the BCK11 catalogue tests.

Human verification focused on whether each request used the expected endpoint, authentication, payload, and HTTP status, and whether its assertions reflected the actual test scenario.

### 2.2. BCK10 — Predefined Pizza Test Corrections

The work included reviewing the Bruno tests for creating and retrieving predefined pizzas, including the files `POST-CREATE-PREDEFINED-PIZZA.yml` and `GET-DETAILS-PREDEFINED-PIZZA.yml`.

A syntax issue involving an extra closing `});` was identified in the test scripts and corrected. The corrected files were then staged for the relevant branch and checked through the normal development workflow. The purpose of the correction was to restore valid test-script structure without changing the intended API behaviour.

### 2.3. BCK11 — Catalogue Tests and Test Data

AI assistance was used to inspect the purpose and dependencies of the catalogue test files, including:

- `01 - List Catalogue.yml`
- `02 - Filter by Category.yml`
- `03 - Exclude Allergens.yml`
- `04 - Filter Available Products.yml`
- `05 - Get Catalogue Item Not Found.yml`
- `06 - Get Catalogue Item (Created Product).yml`
- `07 - Get Predefined Pizza Details.yml`
- `00 - Setup/00 - Setup Available Product.yml`

Particular attention was paid to generated SKUs, setup requests, category filtering, and the relationship between variables created by setup scripts and variables used in assertions. The setup request creates a SKU in `bck11ProductSku`; the listing and category-filter tests also refer to `dualProductSku`. These are distinct variables, so their availability and intended meaning need to be verified when running the collection independently or on a fresh Bruno environment.

### 2.4. Debugging Environment-Dependent Results

AI was used to help separate application defects from test-environment or test-data differences. For API tests, an identical `baseUrl` does not by itself prove that two runs use the same database state, environment variables, token values, or previously created records.

The practical validation approach was to inspect the failing request and assertion, confirm the test setup, and compare the actual response with the expected contract before changing implementation code.

### 2.5. Test and Build Feedback

AI assistance helped interpret test and build output and identify which checks should be repeated after a correction. The reported local Jest run completed with **44 passing test suites, 355 passing tests, and 3 skipped tests**; one suite was reported as skipped. The backend build also completed successfully in the reported run.

These results describe that validation run only. They should not be presented as proof that every Bruno collection passes on every environment unless the complete Bruno collection has also been executed and its output recorded.

## 3. Human Review and Quality Control

The following checks remained the developer's responsibility:

1. Confirm that suggested changes match the real repository files and the intended user story.
2. Preserve the API contract and avoid changing application behaviour merely to make a test pass.
3. Validate syntax, authentication, request payloads, expected status codes, and response assertions.
4. Run the relevant tests and build after changes.
5. Check environment variables and test-data dependencies when results differ between machines.

## 4. Limitations

AI cannot independently establish the state of the local database, the values of a developer's Bruno environment, or the precise commit history unless that evidence is supplied. Those details must be checked in the project environment rather than inferred.

## 5. Conclusion

AI served as a debugging and review assistant for the LaPrizza project, especially for Bruno test maintenance and understanding environment-dependent test behaviour around BCK10 and BCK11. Correctness was established through repository inspection and executable validation, not by accepting AI output without review.
